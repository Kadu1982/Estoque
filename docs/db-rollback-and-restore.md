# Rollback and Restore of Database

## Goal

Define a minimal and verifiable procedure to recover the database after a failed deploy or migration.

## Prerequisites

- Recent backup generated by `infra/scripts/backup-db.sh`.
- Approved maintenance window.
- Staging environment available for rehearsal.

## Recommended flow (staging first)

1. Generate backup before deploy:
```bash
ENV_FILE=/opt/austral-estoque/.env BACKUP_DIR=/opt/backups bash infra/scripts/backup-db.sh
```

2. Apply deploy/migrations in staging.

3. If schema/data fails:
- Restore backup in staging.
- Validate application with smoke test.

4. Repeat in production only after staging succeeds.

## Restore options

Direct restore:
```bash
gunzip -c /opt/backups/<file>.sql.gz | docker exec -i austral-db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

Repository script:
```bash
ENV_FILE=/opt/austral-estoque/.env \
DB_CONTAINER=austral-db \
BACKUP_FILE=/opt/backups/<file>.sql.gz \
FORCE_RESTORE=true \
bash infra/scripts/restore-db.sh
```

## Restore acceptance criteria

- Restore command finishes with no critical SQL errors.
- `GET /actuator/health` returns `UP`.
- Smoke test passes after restore.

## Notes

- Container rollback does not replace schema rollback.
- Every non-reversible migration must have explicit contingency.
